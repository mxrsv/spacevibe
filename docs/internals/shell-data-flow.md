# Shell data flow (redesign frame)

How the redesign's frame gets its data, derives what each page shows, writes and routes. It exists only while `SPACEVIBE_REDESIGN=1` is on in a development build ([`LaunchMode`](../../Sources/SpaceVibe/App/LaunchMode.swift)); the v5 pages keep their own per-page reads ([overview.md](overview.md#data-flow)). The requirements are the [redesign spec](../specs/2026-11-20-spacevibe-redesign.md); the behaviour reference for every derivation is the mock's pure model `world` (`src/m-model.js`, outside git).

## Decisions

- **One store, one talker.** [`FrameStore`](../../Sources/SpaceVibe/Shell/FrameStore.swift) holds the latest `clis.registry`, `inventory.read`, `loadout.rows`, `rules.snapshot` (global plus the Shared and Local file of every project the global reading lists), `limits.read`, the `activity.subscribe` reports, `journal.history` and `findings.kept` (the Keep list). It is the only object of the frame that calls `CoreService`. The app creates it once, inside the one [`FrameModel`](../../Sources/SpaceVibe/Shell/FrameModel.swift) of [`SpaceVibeFrameApp`](../../Sources/SpaceVibe/App/SpaceVibeApp.swift), and hands that model to the main window, the Settings window and the Journal window, so a v5 launch never has one and the three windows read one store.
- **When it reads.** Everything at first appearance; again on app activation, skipped inside `FrameStore.refreshInterval` (10 s, the v5 interval), except Activity, which asks the live subscription for a report on every activation first (`activityRefresh`, GW23); everything on ⌘R. A write re-reads only the sources it names, plus the journal. `clean.scan` is never part of that refresh: it walks every log of every CLI, so only `FrameStore.readClean()` runs it (Clean calls it when the page opens, and ⌘R does), through the `cleanScanner` `FrameModel` sets; Scan Again and a Clean write read it too. One scan runs at a time: a call while one runs joins it and gets its answer, and a write's re-read waits for it and starts its own, since a scan that began before the write cannot see what it moved. The scan's answer is `FrameSnapshot.clean`, and the usage scan's `problems` (an unreadable usage archive) are `FrameSnapshot.usageProblems`, which Clean shows as a band.
- **Pure derivations.** [`FrameWorld`](../../Sources/SpaceVibe/Shell/FrameWorld.swift) is a value built from the store's snapshot, `FrameFacts` and the clock: rows, the Never ran / Dead set, Inbox findings and groups, pace and the Limits hero, Clean's rows and locks, and one `figure(for:)` per page. A page's hero and its sidebar item both call `figure(for:)`, so they cannot disagree. Selection, ticks, filters, scope pickers and popovers are page state and never enter the store or the world. Each page's state object lives in `FrameModel.pageState` (one per type, one per page for Skills and Subagents), because a region's parts are rebuilt on every render; the toolbar's search text is `FrameModel.search`, which filters a page's list and never its hero.
- **One write path.** [`FrameWrites`](../../Sources/SpaceVibe/Shell/FrameWrites.swift) marks the control pending, calls the core, shows the toast (Undo on the returned journal id, or the core's refusal in a danger toast), then re-reads. The new frame's writes are `copyTo`, `removeFrom` and `removeMany` (re-read `inventory.read` and `loadout.rows`), `rules.removeMany` (one write per file, re-reads that file) and `findings.keep` / `unkeep` (re-read the Keep list); each also re-reads the journal. Their toasts are built from the core's answer, in the mock's sentences: `copyTo` names `alsoReaders` ("… read the same folder, so they have it too"), `removeFrom` names `lost` ("Removed pdf-extract from Codex"), `removeMany` counts rows, not copies, names each kind and `lost`, and adds ". settings.json was edited" when a Hook went ("Removed Hook lint-staged.sh from Claude Code. settings.json was edited"). Nothing changes on screen before the core answers. A removal outside Skills and Subagents (Inbox, Clean) names every member that shares a file with the rows, other rows' links included, and an Inbox tile does exactly what the row's logo does ([`RowRemoval`](../../Sources/SpaceVibe/Shell/RowRemoval.swift)), because the engine refuses a removal that leaves a link dangling. A logo or tile press is judged on the store's world at the press, and none starts while another write on its row runs, or while an Undo runs (`FrameWrites.isUndoing`: an Undo may change any row) (D53). Undo goes through `ToastCenter`'s one session stack, which the toast button, ⌘Z and Z all pop (RD39). [`FrameToastHost`](../../Sources/SpaceVibe/Shell/FrameToastHost.swift), mounted once at the frame root, draws the center's toast as `WriteToast` or `RefusedWriteToast` (a refusal stays until dismissed) and, while mounted, takes over the announcement from the center so a refusal is announced at high priority (RD-R16).
- **One route value.** [`FrameRoute`](../../Sources/SpaceVibe/Shell/FrameRoute.swift) is page + selected id + scope. Selecting a row never changes the page; opening another page clears the selection (nothing is pre-selected) and keeps the scope. Opening another page clears the toolbar's search inside `FrameRouter.open`, before the new page's first-row rule (RD44) judges. Window ids are `cli:windowID` and session ids `cli:sessionID`, the ids the countdown pill and the glance widget already use. An outside route (`go(to:)`) keeps the current scope, clears the search and first runs the page's revealer (`setRevealer`; Activity's switches to Sessions and clears a CLI menu that hides the session), so the first-row rule keeps the row it names. `FrameRouter.revision` counts page changes and outside routes only: a page's dialog records it and closes when it moves, never on a selection, a scope or the first-row rule. The widget reaches the route through [`GlanceController.frame`](../../Sources/SpaceVibe/Glance/GlanceController.swift), which `AppFrame` sets when it appears: with it set, a click that falls back to SpaceVibe opens Limits on that Window or Activity on that session in the frame, never in the v5 shell.

## Constraints

- **Never invent a figure (FE-D3).** `FrameFacts` holds the inputs beside the snapshot. The store fills two from the engine: the Keep list from each `findings.kept`, and each Hook row's errors in the last 7 days from the `errorsLast7Days` of its own CLI's cell on each `loadout.rows` (a row whose cells carry no week is absent, unknown rather than 0). Lifetime hook errors never stand in for the 7-day count. Balance pins and hidden CLIs come from Settings › CLIs ([`CLIPreferences`](../../Sources/SpaceVibe/Settings/CLIPreferences.swift), applied in `FrameStore.world`): before the user changes a pin, the first two CLIs that hold Skills or Subagents and own a folder SpaceVibe copies them into (the readers map's `copyTarget` folders, so a CLI that is not installed is skipped) are pinned, as the mock starts. Balance never offers what `Add to` cannot do: no plugin or project item, no CLI without such a folder. Without `clean.scan` Clean's figure is `notMeasured`, never 0.
- **Inbox waits for the Keep list.** Inbox's figure is pending until `findings.kept` answers and failed when it never could be read: the core refuses a list it cannot read instead of reading it as empty, so counting kept findings again would be a made-up count. Kept findings leave the count and the groups and sit in `keptFindings` (`N kept · Show`).
- **Added in the last day is one rule** (`FrameRow.isRecentlyAdded`): a counted zero carries the core's D63 note ("Added in the last 24 hours" or "Added after the newest log"), or, where no cell carries one (a dead Hook that ran, unmeasurable or scanning cells), the row's newest `firstSeen` is under 24 hours before the world's clock. The core decides the note from that same time, so the two agree where both exist.
- **Via, losers and files come from the readers map, not from a rule in the shell.** [`ItemReaders`](../../Sources/SpaceVibe/Shell/ItemReaders.swift) applies the rules of [inventory.md](inventory.md#readers-map) to `loadout.rows`' `folders` and each member's `folder` and `realPath`; a row with a member the table does not name answers `ReadersAnswer.unknown`, never a guess. Removing a file takes every member with its real path from any row, as the engine's removal does ([mutations.md](mutations.md#rules-that-are-easy-to-get-wrong)): a link under another name sits in another row, so the shell counts that link's reader as a loser and among the file's readers, where the engine refuses a removal that does not name it. Whether a rule allows a whole tool is the core's `wide` flag; the shell only keeps the allow ones.
- **The new frame reads `items` and `extraItems` together.** The Codex skills of `~/.agents/skills` are only in `extraItems` (and their problems only in `extraProblems`), because the v5 shell must not see them; a row's members are both lists grouped by key.
- **Never ran is judged over measured CLIs only.** A row is Never ran only when every counted `cliCells` cell is zero and none is unknown; unmeasurable and scanning cells never count. A registry CLI with no cell on a row reads as unknown, never as Missing. A Hook is judged over the cells of the CLIs that hold it only (the mock's `itemStatus`), so an unreadable `~/.codex` makes a Skill with no counted use unknown but never a Claude Code-only Never ran Hook.
- **One CLI per Hook row (RD46).** `FrameRow.rows(from:)` splits a Hook key into one row per CLI, each `<key>@<cli>`, also when one CLI holds it, so a part's id (its selection, ticks, Keep entry, Inbox ids) never changes when another CLI's member comes or goes. Keep entries stored under the former ids (the bare key for Claude Code's part, else the first CLI's) move once per launch after the first reading (`FrameStore.migrateKeptHookIDs`, `FrameRow.keptHookIDMoves`: `findings.keep` the new id, then `findings.unkeep` the old). A part keeps its own CLI's cell, Not supported and Unknown; every other CLI reads Missing, so the Hooks hero, the sidebar, Inbox and Clean count and judge each CLI's Hook alone. The 7-day errors (`FindingFacts.hookErrorsLastWeek`) are keyed by those row ids.
- **Counts that look alike are not the same set.** The Skills, Subagents and Hooks heroes count every Never ran row, plugin and project rows included. Inbox's Clean up and `Select N Suggested` take only the suggested ones: not added in the last day (a counted zero carrying the core's D63 note), not plugin-owned, not a project item, not kept. Clean's Agents section lists every candidate and lets only the writable ones be selected.
- **A hidden CLI still counts where files and locks are concerned.** Show (Settings › CLIs) removes a CLI's rows and sessions from the lists; losers of a removal and Clean's locks still count it. At least one CLI stays shown. A page's `All CLIs` pick on a CLI hidden since reads as All CLIs in its list and its menu (`FrameWorld.shownScope`, `CLIMenuEntries.scope`).
- **Balance pins are none, two or three (RD55).** A switch that would leave one pin moves a second: unpinning one of two unpins the other (Balance off), pinning one when none is pinned pins the first other installed CLI that can be compared (refused when there is none); the Settings toast names it. A stored single pin reads as none.
- **The windows beside the frame share the app's model.** The Settings and Journal windows are their own scenes; the app passes them the same `FrameModel` as the main window, and each calls `start()` (which runs once), so a window opened first still has the registry. The Journal window undoes through `FrameStore.makeWrites(toasts:)`, the same write path with its own toast host and the store's one pending set (`FrameWritesPending`), so the main window's row locks see its Undo; a Journal Undo re-reads every item source, the Keep list, every rules file the store holds and Clean's scan once Clean has read one, because an entry does not say what it touched. Once the core accepted it, the entry's Undo leaves the main window's session stack (`FrameWrites.undoFromJournal`), or a later Z would ask the core to undo it again and be refused.
- **Locks come from the core and fail closed.** Clean's locks and their sentences are `clean.scan`'s (logs: a running or waiting session; caches: any live session or process, or `processUnknown`). The scan is read on demand, so a session the live Activity report shows later adds a lock in the core's words, and a lock is never dropped before the next scan. The core checks again on its own move; the shell's copy only says so before the click.
- **Clean's log age is a fact, not page state.** The 30 / 90 / 180 days control writes `FrameFacts.cleanLogAges`, because what can be cleaned, which the sidebar shows too, depends on it (hero = sidebar).
- **A Clean write is two entries and one Undo.** Equipment goes first through `loadout.removeMany`, then logs and caches through `clean.move`; the toast's one Undo reverts both, newest first (`FrameWriteOutcome.entries`). Once the equipment is gone, a refused, cancelled or partial move is a partial toast (`ToastTone.partial`) with Undo, never a refusal. Cancel cancels the move's own task, so the re-read after it still runs.
- **The registry is the one list of CLIs.** `limits.read` still carries the v5 `gemini` entry; the world drops every CLI the registry does not list.

## Traps

- **Activity has one source at a time.** While the subscription is live the store never calls `activity.read`, because a read that returns late would overwrite a newer push; a write that touched Activity (Stop) asks the subscription for a report now (`activityRefresh`) instead, or the stopped row would stay until the 20 s poll. When the stream fails, a read stands in and the next refresh subscribes again.
- **The scan's follow-up read never starts another scan.** A core that restarted answers `loadout.rows` with `scanning` and no scan running, which starts one; the read that follows a finished scan is excluded, or a core that keeps answering `scanning` would loop.
- **A late answer loses.** Each source has a generation; an answer for an older request is dropped. A failed refresh keeps the last reading (`failed` with data); only a source never read is `failedEmpty`, which makes its page's figure `failed`.
- **A removal that reaches another row goes through `removeMany`.** `loadout.removeFrom` takes CLIs of the row the id belongs to, so a file shared with a link in another row is refused whatever CLIs are named; `ItemReaders.reachesOtherRows` says so before the click, and only `removeMany` with the other row's member id too can take it.
- **Keep ids are the shell's.** The core stores finding ids as given and never reads them, so changing an id shape in [`Findings`](../../Sources/SpaceVibe/Shell/Findings.swift) un-keeps what was kept under the old one. A Window id carries its reset time, so a kept Window comes back with the next Window; a waiting session's id has no wait start, so a kept wait stays kept until the session ends.
- **Rules ids repeat across files.** A rule id is `<scope>:<verdict>:<rule>`, so the same rule in two projects has the same id; finding ids add the project folder. A Rules row's id is `<scope>:<dir>:<rule>` without the verdict (`RulesRuleRow.rowIDs`; a second entry of one text under another verdict adds `#<verdict>`), so a verdict change or its Undo keeps the row selected; the dial matches the core's id (verdict and text) first, by text only when that entry is gone. The core reads an unknown project as global; such a reading is ignored for the project it was asked for.
